## Why This Matters

Deploying Visual Simultaneous Localization and Mapping (VSLAM) on physical humanoid robots represents the critical transition from simulation to real-world operation. Unitree robots like the Go2 and G1 provide excellent platforms for VSLAM research with integrated stereo cameras, IMUs, and powerful onboard compute. Understanding how to deploy VSLAM safely on these platforms is essential for robotics researchers working on autonomous navigation in unstructured environments.

**Real-World Applications**:
- **Search and Rescue**: Autonomous exploration of disaster zones using visual SLAM
- **Industrial Inspection**: Navigation in GPS-denied industrial facilities
- **Healthcare Assistance**: Indoor navigation for elderly care and hospital delivery
- **Space Exploration**: Autonomous navigation in extraterrestrial environments

:::danger Hardware Safety
Before deploying any motor control code to Unitree hardware:
- Ensure emergency stop procedures are tested and accessible
- Verify Dead Man Switch patterns with 100ms timeout are implemented
- Test all safety limits in simulation before physical deployment
- Have a human operator ready to take manual control if needed
- Maintain safe operational boundaries and workspace constraints
:::

### VSLAM Requirements on Unitree

Deploying VSLAM on Unitree platforms requires special consideration:

- **Computational Constraints**: Limited power envelope (200-500W) vs. VSLAM computational demands
- **Dynamic Motion**: Legged locomotion creates vibration and motion blur in camera feeds
- **Real-Time Requirements**: Need to maintain balance while processing visual data
- **Safety Critical**: Navigation errors can cause falls or collisions

```python
        self.declare_parameter('max_linear_velocity', 0.5)  # 0.5 m/s max
        self.declare_parameter('max_angular_velocity', 0.5)  # 0.5 rad/s max

        self.safety_enabled = self.get_parameter('safety_enabled').value

        qos_profile = QoSProfile(
            history=QoSHistoryPolicy.KEEP_LAST,
            depth=1,
            reliability=QoSReliabilityPolicy.RELIABLE,  # Critical for safety
        )

        # Subscribers for safety monitoring
        self.cmd_vel_sub = self.create_subscription(
            Twist,
            '/cmd_vel_safety_filtered',  # Filtered commands from higher level
            self.cmd_vel_callback,
            qos_profile
        )

            JointState,
            '/joint_states',

            Imu,
            '/imu/data',

            qos_profile
        )

        self.safety_status_pub = self.create_publisher(Bool, '/safety_ok', qos_profile)

        self.last_cmd_vel = Twist()
        self.current_joint_states = JointState()

        self.balance_ok = True
        self.velocity_safe = True
        self.emergency_stop_active = False

        self.safety_timer = self.create_timer(0.01, self.safety_check)  # 100Hz

            # Check velocity limits
            if abs(msg.linear.x) > self.max_lin_vel:
                self.get_logger().warn(f'Linear velocity limit exceeded: {msg.linear.x}')
                msg.linear.x = max(min(msg.linear.x, self.max_lin_vel), -self.max_lin_vel)

            if abs(msg.angular.z) > self.max_ang_vel:
                self.get_logger().warn(f'Angular velocity limit exceeded: {msg.angular.z}')
                msg.angular.z = max(min(msg.angular.z, self.max_ang_vel), -self.max_ang_vel)

            self.last_cmd_vel = msg
            self.last_cmd_time = self.get_clock().now()

        """Monitor joint states for safety."""
        with self.safety_lock:
            self.current_joint_states = msg

        with self.safety_lock:
            self.current_imu = msg

            # Convert quaternion to Euler angles (simplified)
            # In practice, use tf2 for proper quaternion conversion

                elif not self.balance_ok:
                    self.get_logger().error('BALANCE THRESHOLD EXCEEDED - STOPPING FOR SAFETY')
```

## Physical Deployment Procedures

### Pre-Deployment Safety Checklist

Before deploying VSLAM to physical hardware, complete this checklist:

1. **Software Safety Systems**:
   - [ ] Dead Man Switch timeout implemented (100ms)
   - [ ] Velocity limits enforced
   - [ ] Balance monitoring active
   - [ ] Emergency stop procedures tested

2. **Hardware Safety Systems**:
   - [ ] Physical emergency stop button accessible
   - [ ] Safe operational boundaries established
   - [ ] Fall protection measures in place
   - [ ] Collision avoidance sensors functional

3. **Simulation Validation**:
   - [ ] VSLAM pipeline tested in Gazebo simulation
   - [ ] Navigation algorithms validated in Isaac Sim
   - [ ] Safety controller behavior verified in simulation

### Deployment Process

1. **Initial Setup**:
```bash
# SSH to Unitree robot
ssh unitree@192.168.123.161

# Source ROS 2 environment
source /opt/ros/humble/setup.bash
source ~/unitree_ws/install/setup.bash

# Launch safety controller first
ros2 launch unitree_ros unitree_safety.launch.py
```

2. **VSLAM Pipeline Launch**:
```bash
# Launch VSLAM with safety integrator
ros2 launch orb_slam3_ros unitree_stereo.launch.py \
  config_path:=~/config/orb_slam3_unitree.yaml \
  vocabulary_path:=~/ORBvoc.txt

# Launch safety integrator
ros2 run unitree_vslam vslam_safety_integrator
```

3. **Monitoring During Operation**:
```bash
# Monitor safety status

# Monitor navigation commands

# Monitor robot state
```

## Troubleshooting Common Issues

### VSLAM Tracking Loss

**Problem**: VSLAM loses tracking during dynamic motion
**Solutions**:
- Reduce robot speed during challenging terrain
- Increase feature extraction parameters
- Use IMU data to improve tracking during motion
- Implement loop closure detection for relocalization

### Safety System False Positives

**Problem**: Safety system stops robot unnecessarily
**Solutions**:
- Fine-tune balance thresholds for specific terrain
- Adjust Dead Man Switch timeout for communication delays
- Verify IMU calibration
- Test with different locomotion gaits

### Computational Overload

**Problem**: VSLAM causes computational overload on robot
**Solutions**:
- Reduce image resolution or frame rate
- Use faster feature descriptors
- Implement multi-threading for heavy computations
- Offload to external compute if possible
